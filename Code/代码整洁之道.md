## 一句话总结

整洁代码不是“写完以后再打扫”，而是在每一次命名、拆分、抽象、测试和提交中持续维护表达力，让后来者能快速看出代码在解决什么问题，以及为什么这样解决。

## 核心原则

- 童子军军规同样适用于代码：离开时要比发现时更整洁。
- 勒布朗法则：稍后等于永不。
- 整洁代码只做好一件事。
- 代码应该讲述事实，不引人猜测。
- 消除重复，提高表达力，并用简单抽象降低理解成本。
- 专业程序员不仅让代码能运行，还要让代码能被阅读、修改和信任。

## 一、前言和整洁代码

### 整洁代码的基本理念

- “整洁代码派”的基本理念是不断迭代，而不是等待一次大型重写。
- 良好的软件实践需要专注、镇定和思考。
- 代码会长期存在，因此我们不能抛弃必要的精确性。
- 写整洁代码需要大量小技巧，更需要通过实践获得“代码感”。

### 5S 与软件实践

- 全员生产维护：Total Productive Maintenance, TPM。
- 5S 哲学是精益思想的基石：
  - 整理：区分有用与无用。
  - 整顿：每个东西都有合适位置。
  - 清扫：持续清除混乱。
  - 清洁：形成标准。
  - 素养：把标准变成习惯。

### 书中金句

- 物皆有其位，而后物尽归其位：A place for everything, and everything in its place.
- 整洁近乎虔诚：Cleanliness is next to godliness.
- 守小节者不亏大节：He who is faithful in little is faithful in much.
- 及时一针省九针：A stitch in time saves nine.
- 今日事今日毕：Do not put off until tomorrow what you can do today.

### 对整洁代码的理解

Grady Booch 认为，整洁代码应当简单直接，像优美的散文一样展示设计者的意图，具有干净利落的抽象和直截了当的控制语句。

可以把“整洁”理解为三层能力：

- 读得懂：命名、结构和格式能让读者快速进入上下文。
- 改得动：职责清楚，耦合可控，测试能提供反馈。
- 信得过：边界、错误处理和并发语义明确，行为不靠猜。

## 二、有意义的命名

### 命名原则

- 名副其实：名称应该回答“它是什么”和“它为什么存在”。
- 避免误导：不要用和实际类型、行为或领域概念冲突的名字。
- 做有意义的区分：不要用 `data`、`info`、`manager` 这类空泛后缀制造差异。
- 使用读得出来的名称：便于讨论、搜索和代码评审。
- 使用可搜索的名称：名称长短应该与作用域大小相匹配。
- 避免思维映射：明确是王道，不要要求读者在脑中翻译缩写。

### 类名与方法名

- 类名和对象名应该是名词或名词短语。
- 方法名应该是动词或动词短语。
- 布尔方法可以用 `is`、`has`、`can`、`should` 等前缀表达判断语义。
- 获取、修改和转换操作应该保持一致命名，例如 `get`、`set`、`to`、`from`。

### 避免编码

- 避免匈牙利命名法。
- 避免成员前缀，除非团队已有强约定。
- 接口和实现的命名应该服务于业务含义，而不是暴露技术细节。

### 统一词汇

- 每个概念对应一个词，例如不要在同一系统里混用 `fetch`、`retrieve`、`get` 表示同一种动作。
- 别用双关语，同一个词不要在不同上下文里表示不同含义。
- 优先使用解决方案领域名称，例如 `Queue`、`Repository`、`Factory`。
- 当业务语义更重要时，使用问题领域名称，例如 `Order`、`Policy`、`Settlement`。

### 补充示例

```java
// 不够清楚
int d;

// 更清楚
int elapsedTimeInDays;
```

```java
// 空泛
class UserManager {}

// 更具体
class UserRegistrationService {}
```

## 三、函数

### 短小

- 函数应该短小。
- 函数应该只做一件事，做好这件事，只做这一件事。
- 判断函数是否做了多件事，可以看它是否还能再拆出一个有独立意义的函数。

### 抽象层级

- 每个函数内部应该保持一个抽象层级。
- 代码应该能自顶向下阅读，这就是“向下规则”。
- 高层函数描述意图，低层函数承接细节。

### 设计原则

- 单一职责原则：Single Responsibility Principle, SRP。
- 开放闭合原则：Open Closed Principle, OCP。
- 不重复自己：Do not Repeat Yourself, DRY。

### 使用描述性名称

- Ward 原则：如果每个例程都让你感到深合己意，那就是整洁代码。
- 命名方式要保持一致。
- 别害怕长名称，清楚比短更重要。

### 函数参数

- 参数越少越好。
- 无参数最好，一个参数可以接受，两个参数需要谨慎，三个及以上通常应该重新审视设计。
- 避免布尔参数，因为它通常暗示函数在做两件事。
- 多个相关参数可以封装为值对象。

### 副作用和命令查询分离

- 函数名承诺了一件事，就不应该偷偷做另一件事。
- 查询函数应该返回信息，命令函数应该改变状态，二者尽量分离。
- 使用异常替代错误码，避免调用方遗漏错误处理。

### 补充示例

```java
// 布尔参数让函数出现两种行为
renderPage(true);

// 拆成两个更明确的动作
renderPageForPreview();
renderPageForPublish();
```

## 四、注释

### 注释的定位

真实只在一处地方有：代码。只有代码能忠实地告诉你它做了什么。

注释不是坏事，但它往往是在补偿代码表达力不足。优先改进命名、拆分函数和调整结构；当这些方式仍不足以解释背景、风险或决策时，再写注释。

### 好注释

- 法律信息，例如版权和许可证。
- 解释意图，说明为什么这样做。
- 阐明晦涩处，例如外部系统限制、兼容逻辑、性能权衡。
- 警示后果，例如某段逻辑不能随意调整的原因。
- TODO 注释，前提是可搜索、可追踪、能被定期清理。

### 坏注释

- 喃喃自语。
- 多余的注释。
- 误导性注释。
- 循规性注释。
- 日志式注释。
- 废话注释。
- 能用函数或变量表达时仍使用注释。
- 位置标记。
- 括号后面的注释。
- 归属与署名。
- 注释掉的代码。
- HTML 注释。
- 非本地信息。
- 信息过多。
- 不明显的联系。
- 函数头。

### 补充示例

```java
// 差：重复代码
i++; // increment i

// 好：解释业务原因
// 供应商接口会在月底返回重复账单号，因此这里使用交易流水号去重。
deduplicateByTransactionId(records);
```

## 五、格式

格式的目的：即便代码已不复存在，你的风格和律条也会存活下来。

### 垂直格式

- 短文件通常比长文件更容易理解。
- 向报纸学习：顶部给出高层概念，细节向下逐步展开。
- 概念之间用空白行隔开。
- 关系密切的概念应该相互靠近。
- 变量声明应尽可能靠近使用位置。
- 相关代码放在一起，相关性越强，距离越短。

### 横向格式

- 尽量保持代码行短小，可用团队约定的 100 或 120 字符作为边界。
- 水平方向上的空格应该表达关系，例如运算符两侧、参数之间。
- 不要为了对齐制造大面积空白，对齐一旦变动会产生无意义 diff。
- 缩进表达层级，层级过深往往提示需要拆分。

### 团队约定

- 格式应由自动化工具保障，例如 formatter、linter、editorconfig。
- 代码评审不应该反复争论可由工具解决的排版问题。

## 六、对象和数据结构

### 数据抽象

- 抽象的本质不是简单地在变量外面包一层函数，而是隐藏实现细节。
- 隐藏数据结构时，应该暴露有业务意义的操作，而不是机械地提供 getter 和 setter。
- 对象和数据结构具有反对称性：对象易于新增类型，数据结构易于新增操作。

### 对象与数据结构的差异

- 对象隐藏数据，暴露行为。
- 数据结构暴露数据，由外部函数操作。
- 二者都合理，但混在一起会制造混乱。

### 得墨忒耳律（The Law of Demeter）

模块不应了解它所操作对象的内部情形。直观地说，不要写长长的调用链去穿透对象内部。

类 `C` 的方法 `f` 只应该调用以下对象的方法：

- `C` 自身。
- 由 `f` 创建的对象。
- 作为参数传递给 `f` 的对象。
- 由 `C` 的实体变量持有的对象。

```java
// 暴露内部结构
String city = order.getCustomer().getAddress().getCity();

// 让对象提供业务语义
String city = order.customerCity();
```

方法不应调用由任何函数返回对象的方法。换言之，只跟朋友谈话，不跟陌生人谈话。

连续的访问链容易变成“火车失事”式代码，暴露对象内部结构，也常常提示特性依恋（Feature Envy）。

### 常见形态

- 数据传送对象（Data Transfer Object, DTO）：只承载数据，不承载业务行为。
- Active Record：同时保存数据并提供持久化操作，适合简单场景，但容易把数据结构和对象行为混在一起。
- 特性依恋（Feature Envy）：一个函数过度使用另一个对象的数据，可能应该移动到被依恋的对象中。

### 取舍

- 当新增类型更频繁时，对象更合适。
- 当新增操作更频繁时，数据结构加独立函数可能更直接。

## 七、错误处理

错误处理很重要，但如果它搞乱了代码逻辑，就是错误的做法。

### 原则

- 使用异常而不是错误码，让主流程保持清晰。
- 先写 `try-catch-finally` 的范围，再填入业务逻辑。
- 优先使用未检异常，避免把错误处理细节层层污染到调用链。
- 异常应该提供足够上下文，便于定位问题。
- 按调用者需要定义异常类型，而不是直接暴露底层实现异常。
- 不要返回 `null`，也不要把 `null` 传来传去。
- 使用特例模式（Special Case Pattern, Fowler）或空对象表达“没有结果”，减少空值判断。

### 边界

- 不要吞掉异常。
- 不要用异常控制正常流程。
- 低层异常应在合适边界转换成领域可理解的异常。

## 八、边界

### 第三方代码

- 第三方库的接口通常比业务需要更宽，建议用薄封装隔离。
- 不要让外部库类型在业务核心中四处扩散。
- 学习性测试可以用来理解和固定第三方库行为。

### 学习性测试

不要在生产系统中试验新东西，而是编写测试来浏览、学习和固定第三方代码的行为。Jim Newkirk 把这叫作学习性测试（learning test）。

学习性测试的价值不只是“免费”覆盖第三方库，还包括：

- 帮助团队理解第三方 API 的真实行为。
- 在升级依赖时快速发现行为变化。
- 把边界处的假设留成可执行文档。

### 尚未存在的代码

当依赖的外部系统尚不可用时，可以先定义自己期望的接口，再用适配器连接真实实现。这样业务代码依赖的是稳定意图，而不是不确定细节。

### 整洁的边界

边界上的代码需要清晰分割，并用测试定义期望行为。应该避免让业务代码过多了解第三方代码中的特定信息。

- 依靠能控制的东西，好过依靠控制不了的东西，免得日后受其牵制。
- 只在少数几个位置引用第三方边界接口。
- 对 `Map` 等通用集合做业务化封装，限制外部 API 的扩散。
- 使用适配器模式把第三方接口转换成内部期望的接口。

## 九、单元测试

TDD 三定律：

1. 在编写不能通过的单元测试前，不可编写生产代码。
2. 只可编写刚好无法通过的单元测试，不能编译也不算通过。
3. 只可编写刚好足以通过当前失败测试的生产代码。

保持测试整洁：测试代码和生产代码一样重要。测试带来一切好处，但前提是测试本身也值得维护。

整洁测试的核心是可读性、可读性和可读性：

- 明确、简洁，并有足够表达力。
- 可以形成面向特定领域的测试语言。
- 允许测试代码和生产代码存在合理的“双重标准”，但不能牺牲可读性。
- 倾向于 `given-when-then` 结构。
- 单个测试中的断言数量应该最小化。
- 每个测试只验证一个概念。

### 测试的重要性

- 测试让重构变得可持续。
- 没有测试的代码很难保持整洁，因为修改成本太高。
- 测试代码和生产代码一样需要整洁。

### F.I.R.S.T 原则

- Fast：快速。
- Independent：彼此独立。
- Repeatable：可重复。
- Self-validating：自验证。
- Timely：及时编写。

### 测试可读性

- 一个测试表达一个行为。
- 测试名应该描述场景和预期。
- 测试数据要突出差异，避免无关噪声。

## 十、类

### 类应该小

- 类的大小用职责衡量，而不是用行数衡量。
- 如果很难给类起一个简洁名称，通常说明职责过多。
- 类应该只有一个修改理由。

### 内聚

- 类中的方法和变量应该围绕同一组概念。
- 当类内只有少数方法使用某些字段时，可能该拆出新类。

### 依赖

- 依赖抽象，不依赖具体实现。
- 通过接口、工厂或依赖注入降低测试成本。

## 十一、系统

### 构造与使用分离

- 对象创建是一个关注点，对象使用是另一个关注点。
- 把启动、装配、配置逻辑放在边界处，不要混入业务流程。

### 渐进式架构

- 系统架构应能逐步生长。
- 不要为了未来的想象过度设计，但要留下清晰的扩展边界。
- 领域语言应进入代码，让系统表达业务意图。

## 十二、迭进

Kent Beck 的简单设计规则可以作为整洁代码的落地顺序：

1. 通过所有测试。
2. 消除重复。
3. 表达程序员意图。
4. 最小化类和方法数量。

这四条不是一次性完成的，而是在持续重构中反复靠近。

## 十三、并发

### 并发的难点

- 并发会放大偶发性问题。
- 失败通常不可稳定复现。
- 正确性、性能和可读性之间更容易互相牵制。

### 实践建议

- 分离并发策略和业务逻辑。
- 限制共享数据范围。
- 优先使用不可变对象。
- 尽量使用成熟的并发库和线程安全集合。
- 编写能施压的测试，但不要假设测试能证明并发完全正确。

## 十四、逐步改进

整洁不是第一次写出来的，通常是先让代码工作，再让代码正确，最后让代码清楚。

重构时可以采用小步策略：

1. 为当前行为补测试。
2. 找到最刺眼的重复或混乱。
3. 做一个可回滚的小修改。
4. 运行测试。
5. 继续下一个小修改。

## 十五、坏味道与启发式规则

### 常见坏味道

- 重复。
- 过长函数。
- 过大的类。
- 过长参数列表。
- 神秘命名。
- 布尔参数。
- 隐藏副作用。
- 不一致的抽象层级。
- 对第三方库的扩散依赖。
- 被注释掉的代码。
- 测试难以编写或难以理解。

### 判断问题的提问

- 这段代码的意图是否一眼可见？
- 我能安全修改它吗？
- 修改一个需求需要碰多少地方？
- 命名是在解释业务，还是在解释实现细节？
- 测试失败时，我能快速知道哪里坏了吗？

## 实践清单

提交前可以快速过一遍：

- 名称是否准确、可搜索、无误导？
- 函数是否短小，且只处在一个抽象层级？
- 是否存在可以消除的重复？
- 注释是否解释了原因，而不是复述代码？
- 错误处理是否让主流程保持清晰？
- 外部库、IO、时间、随机数等边界是否被隔离？
- 是否有足够测试支撑重构？
- 格式是否由工具统一？
